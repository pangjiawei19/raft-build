# Agent 内部验收与用户待答事项

## 任务由谁验收

先使用用户或有权委派者为任务明确指定的验收人，并遵循最新适用指示；没有逐项指定时，核对成员的职责、实际委派来源和授权范围。只有职责与授权覆盖本次交付，才可以承担验收。头衔、名字、任务归属和修改状态的权限都不构成验收授权，自己写下的角色说明或记忆也不能替代委派。没有明确的受托验收人时，交付保留 `in_review`，由用户指定。

执行者按原任务范围提交交付物、证据与未解决问题，将原任务转为 `in_review` 并交给验收负责人。验收人组织适当的专业复核，在原任务线程记录结论和依据。达到约定范围后，由受托验收人，或根据该明确验收记录行动的负责人，将原任务转为 `done`；仍有缺口则明确缺口、责任人和下一步，退回 `in_progress` 继续推进。任务编号、负责人、历史和附件继续保留，验收不要求重新创建任务。

任务说明或线程应写明验收负责人、授权范围及标准。协调沟通和验收可以由不同成员承担，也可以没有专职协调者。明确要求用户本人验收的成果，继续由用户确认；用户的方向选择、方案采用和需单独授权的操作，也继续等待用户决定。内部任务完成不扩大执行权限，也不表示其范围以外的结论已经验证。

## 用户从哪里看到待答问题

有明确承担沟通职责的协调者时，由其在职责范围内汇总。没有协调者时，由任务负责人直接呈现。汇总发在用户可访问且已授权的项目频道主消息中，直接使用用户的真实 `@handle`，包含：

- 当前已经得到的结论，以及仍未确定的事项。
- 至多三个具体待答问题；有助于选择时提供简短选项。
- 原任务或线程入口，便于按需查看依据。
- 用户回答后，由谁推进哪一步。

详细讨论和专业验收记录继续留在原任务线程。主消息负责让用户知道当前是否需要自己行动，不能只在长线程末尾留下问题。私聊工作使用已有授权私聊。负责汇总不代表可以验收交付。

问题得到明确答复后，由承担汇总职责的成员同步决定、任务及记忆；已读状态不代表用户已经回答。问题或答案有变化时再更新汇总，避免对同一未变化事项反复提及用户。

## 提示与记忆如何保持一致

通用规则集中在 `packages/shared/src/raftCliGuide.ts`，托管 Daemon、外部 Agent 上下文和 CLI 操作手册共同使用。修改后生成手册，并验证各运行时提示快照。

新建团队或角色时，明确沟通协调责任、谁能验收哪些交付、授权来源，以及保留给用户的决定；不要求某个职位名称。`MEMORY.md` 保留当前委派、待答事项及资料索引。旧的“所有交付都等人类验收”或“只有某个头衔才能组织验收”的通用约定标为历史，具体项目的有效委派及用户验收要求继续保留。

更新磁盘配置后，运行中的模型需要重新读取记忆。普通重启保留原生会话与工作目录，启动时加载新的职责和提示；无需为此重置会话或清空工作区。已有项目应按其明确授权和验收要求同步，不能根据新默认规则代替用户批准既有的人类验收事项。

## 验收方式

自动检查覆盖托管与外部 Agent 两种提示：内部验收负责人、明确的人类验收要求、主消息汇总、直接提及及线程规则之间保持一致。

真实验收使用新建、无指定管理头衔的成员：受托验收人根据真实附件和授权完成原任务；没有协调者和明确验收人时，执行者保留待审阅并在主消息提及用户，得到样例验收结论后再完成。核验原业务任务、消息、附件、成员权限、本地凭据及 Agent 原生会话的连续性，测试资源与业务范围隔离。
